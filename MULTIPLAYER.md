# blobrogue multiplayer (Convex)

Real-time co-op, logins, and saved stats, powered by [Convex](https://convex.dev).
This document is written for **the operator (Ian's box)** who provisions and deploys
Convex. The agent that wrote this **cannot** run Convex (no credentials), so the code
here is complete and compiling but the deployment has not been created yet.

> **The game runs fully in solo mode with zero Convex configuration.** If
> `VITE_CONVEX_URL` is unset, the online layer stays dormant, the menu hides host/join,
> and play is identical to v0. Provisioning Convex only *adds* co-op + accounts.

---

## 1. What you need to run (TL;DR)

```bash
# from the repo root, with Ian's Convex account available to the CLI

npm install                       # convex is already a dependency

# First time only: create the Convex project + generate convex/_generated,
# and push the schema + functions to a dev deployment. Leave it running while
# you develop; it also writes CONVEX_DEPLOYMENT + VITE_CONVEX_URL into .env.local.
npx convex dev

# In another terminal, run the game against that dev deployment:
npm run dev

# When ready for production: push functions to the prod deployment.
npx convex deploy                 # prints your prod URL: https://<name>.convex.cloud
```

Then in **Vercel → Project → Settings → Environment Variables**, add:

| Variable          | Value                                   | Environments            |
| ----------------- | --------------------------------------- | ----------------------- |
| `VITE_CONVEX_URL` | your **prod** URL (`https://….convex.cloud`) | Production (+ Preview if you want co-op on previews) |

Vercel's build command is unchanged (`npm run build`); Vite inlines `VITE_CONVEX_URL`
at build time. Redeploy and co-op is live. Done.

### Optional one-step Vercel integration
If you'd rather have Vercel deploy the Convex functions on every build (instead of you
running `npx convex deploy` by hand):

1. In the Convex dashboard, generate a **Production Deploy Key**.
2. Add it to Vercel as `CONVEX_DEPLOY_KEY`.
3. Set the Vercel **Build Command** to:
   ```
   npx convex deploy --cmd 'npm run build'
   ```
   `convex deploy` pushes the functions, injects `VITE_CONVEX_URL` into the build
   subprocess automatically (it knows Vite), then runs the Vite build.

Either path works. The manual path (set `VITE_CONVEX_URL` + `npx convex deploy` from your
box) matches how you said you'd do it, so it's the default; `vercel.json` is left as
`npm run build` so a deploy **without** any Convex config still succeeds (solo).

## 2. Architecture

The client is **vanilla TypeScript** (no React), so it uses the vanilla
`ConvexClient` from `convex/browser` with `.onUpdate()` subscriptions — not the React
bindings.

### The `_generated` question (why the build works with no deployment)
- The **client never imports `convex/_generated`.** It builds typed function references
  with `makeFunctionReference` from `convex/server` in [`src/net/api.ts`](src/net/api.ts).
  That's what lets `tsc && vite build` pass on a machine that has never run Convex.
- The **backend** (`convex/*.ts`) uses the normal generated imports
  (`./_generated/server`, `./_generated/dataModel`). Those files are **not** part of the
  app's `tsconfig` (`"include": ["src"]`), so they never affect `npm run build`. They are
  type-checked and codegen'd when you run `npx convex dev` / `npx convex deploy`.
- `convex/_generated` is git-ignored (regenerated by the CLI).

### Data model — [`convex/schema.ts`](convex/schema.ts)
- **`players`** — persistent identity + all-time stats: `clientId` (see identity below),
  `name`, `totalKills`, `deepestFloor`, `totalCoins`, `gamesPlayed`, `unlocks[]`.
- **`rooms`** — a co-op lobby / running game: short `code`, `hostPlayerId`, `seed`,
  `floor`, `status` (`lobby | playing | ended`). The `(seed, floor)` pair is the shared
  source of truth that makes everyone generate the same dungeon.
- **`presence`** — live per-player state within a room: `x/y`, `facing`, `hp/maxHp`,
  `weapon`, `floor`, `down`, `aimAngle`, `shotSeq`, `kills`, `colorIndex`, `reviveNonce`,
  `updatedAt`. Synced ~11×/sec.

### Functions
- [`convex/players.ts`](convex/players.ts): `ensurePlayer` (login/upsert), `getProfile`,
  `recordRun` (fold a finished run into all-time stats on game over).
- [`convex/rooms.ts`](convex/rooms.ts): `create` (returns a share code), `join`, `get`,
  `start` (host flips lobby → playing), `descend` (monotonic shared floor), `leave`
  (reassigns host / ends empty rooms).
- [`convex/presence.ts`](convex/presence.ts): `update` (throttled state sync), `list`
  (everyone alive & syncing; stale rows auto-hidden after 12s), `revive`.

### Client
- [`src/net/config.ts`](src/net/config.ts) — reads `import.meta.env.VITE_CONVEX_URL`;
  `isMultiplayerEnabled` gates the whole online layer.
- [`src/net/session.ts`](src/net/session.ts) — identity + saved stats.
- [`src/net/multiplayer.ts`](src/net/multiplayer.ts) — one co-op session: owns the room +
  presence subscriptions and implements the game's `CoopBridge`. The game core
  ([`src/game/game.ts`](src/game/game.ts)) talks only to `CoopBridge`
  ([`src/game/coop.ts`](src/game/coop.ts)) and never imports Convex, so solo has zero
  network code in its graph.
- [`src/ui/menu.ts`](src/ui/menu.ts) — title, co-op lobby (shareable code), game over.

## 3. Identity & saved data — the approach, and why

**Chosen: lightweight persistent identity** — each browser mints a random UUID
(`clientId`) stored in `localStorage`, plus a display name. On boot the client calls
`players.ensurePlayer({ clientId, name })`, which upserts one `players` row and returns
the saved profile. Stats (`recordRun`) key off `clientId`, so they **persist across
sessions** and show on the title screen and the hold-**Tab** stats panel.

**Optional accounts via `@convex-dev/auth` (Google).** The guest path above is still
the default and needs zero config. On top of it, players can *optionally* sign in with
Google (Convex-native auth). When signed in, their stats row keys off the authenticated
`userId` instead of the browser `clientId`, and on first sign-in the current browser's
unowned guest row is migrated onto the account (non-destructive — nothing is deleted and
rows owned by others are never touched). Signing out returns to guest play.

`@convex-dev/auth` ships only React bindings, so the vanilla client reimplements its
small, framework-agnostic protocol directly against the Convex auth actions +
HTTP routes (see [`src/net/auth.ts`](src/net/auth.ts)): `signIn("google")` → OAuth
redirect → code exchange → JWT attached to the live `ConvexClient` via `setAuth`. The
backend is the standard setup: [`convex/auth.ts`](convex/auth.ts),
[`convex/auth.config.ts`](convex/auth.config.ts), [`convex/http.ts`](convex/http.ts),
and `authTables` spread into the schema. **The operator finishes setup — see
[`AUTH_SETUP.md`](AUTH_SETUP.md).** Until then the sign-in button is present-but-inert
and the game is unaffected.

**Trade-off for guests (documented on purpose):** a client-minted id is not a security
boundary — someone could copy another player's `clientId` and assume their stats. That's
acceptable for a co-op shooter with cosmetic all-time stats (no competitive leaderboard /
anti-cheat here). Signing in with Google gives a real, hardened identity for players who
want one.

## 4. The co-op model (what's synced, what's local)

Delivered (the task's "at minimum", plus the down/revive nice-to-have):

- **Same dungeon for everyone** — shared `seed` + `floor`; both the layout and the enemy
  spawns are fully deterministic (seeded RNG in [`src/game/rng.ts`](src/game/rng.ts)), so
  every client generates identical rooms and identical starting enemies.
- **See each other move** — positions/facing/hp/weapon via `presence`, rendered as
  hue-tinted heroes with name labels.
- **See each other shoot** — a per-player `shotSeq` counter; when it ticks up, teammates
  flash a tracer + muzzle in that player's aim direction.
- **Descend together** — reaching the exit calls `rooms.descend`, bumping the room's
  shared floor; everyone follows to the same next floor.
- **Down-but-not-out + revive** — at 0 HP with a living teammate you go *down* (not dead);
  a teammate standing on you for ~1.1s revives you (`presence.revive` bumps `reviveNonce`,
  which your own client observes).

**Client-authoritative-per-client enemies (the honest limitation):** enemies are
simulated locally on each client from the shared seed. They start identical everywhere,
but each player damages their *own* copy — there is no server-authoritative enemy state.
This is the documented "stretch" that was left out to keep things robust and shippable.
The seam for adding it later is clean: make the host authoritative and add an
`enemies` table synced like `presence`; the game already funnels co-op through
`CoopBridge`.

```
  config.ts        VITE_CONVEX_URL gate

```
